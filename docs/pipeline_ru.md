Как работает мой CI/CD pipeline:

В качестве проекта используется самописное приложение anime-backlog-web, с отдельными docker-контейнерами для бекенда на python, фронтенда на Node.js/Next.js и базы данных на postgres.

Подготовка базы для deployment: с помощью Terraform создаю виртуальную машину на yandex cloud. В главном файле Terraform запрашиваю следующее: 1 загрузочный диск, 1 виртуальную сеть, 1 подсеть, 1 виртуальную машину с минимальными характеристиками, подключение загрузочного диска и сети. Первоначальная настройка виртуальной машины осуществляется с помощью Cloud init (выполняется один раз при первом запуске виртуальной машины): добавляет пользователя,  ssh-ключ и так далее. Далее с помощью Ansible происходит более детальная настройка облачной виртуальной машины (устанавливается и конфигурируется docker, firewall, fail2ban, настраиваются опции sshd для увеличения безопасности и так далее). После terraform+cloud init+ansible облачная виртуальная машину полностью готова для деплоя приложения.      

Делаю git push в удаленный репозиторий на github, далее github стучится в endpoint jenkins'а по адресу https://jenkins.bernd32.xyz/github-webhook/. Примечание: сам jenkins доступен по адресу https://jenkins.bernd32.xyz, но только для IP-адресов, определенных в конфигурации nginx. Endpoint для вебхуков https://jenkins.bernd32.xyz/github-webhook/ доступен для всех ip-адресов, но при этом имеется защита в виде верификации payload'а HMAC-подписью.

Далее jenkins клонирует удаленный репозиторий и считывает файл jenkins/Jenkinsfile, который представляет из себя декларативный (pipeline) CI/CD-пайплайн. Сперва идёт этап Quality Gates, в котором параллельно, каждый в своем docker-контейнере, прогоняются тесты фронтенда и бэкенда. Backend: контейнер python:3.14-slim-bookworm, создаёт venv, ставит зависимости (-e ".[dev]"), гоняет pytest с JUnit-отчётом. В post.always публикует результаты тестов. Frontend: контейнер node:22-bookworm-slim, npm ci, typecheck, npm test (vitest, JUnit-отчёт), npm run build. Аналогично публикует отчёт в post.always.

Далее идут этапы сборки docker-образов и их выгрузка на registry (в моем случае это dockerhub) с присваиванием тегов git-sha, которые дают воспроизводимость (можно откатиться на конкретный тег) и историю образов.

Проверка на безопасность происходит следующим образом:

- pip-audit — сканирует Python-зависимости бэкенда

- npm audit — сканирует зависмости фронтенда (js/ts)

- Trivy — сканирует уже собранный Docker-образ целиком (идет сразу после этапа сборки образов)

Чтобы не фейлить сборку, проверка безопасности проходит в non-blocking режиме, предоставляя отчёты по безопасности в панели jenkins.

Далее происходит этап деплоя проекта:

    На удалённом хосте виртуальной машины, с подключённым секретным env-файлом (withCredentials, сам .env файл не коммитится в удаленный репозиторий), запускается docker compose up -d --remove-orphans --wait с только что собранными образами. После успешного пайплайна — очистка неиспользуемых Docker-образов на удалённом хосте (docker image prune -f). Готовый проект становится доступным по адресу http://cloud-ip:20773

Дополнительно: в Grafana добавлен дашборд с мониторингом локального сервера, на котором установлена “production” версия приложения. С помощью стека Prometheus + cAdvisor/node-exporter отслеживается общее состояние сервера (CPU/RAM/disk IO), а также состояния docker-контейнеров (использование файловой системы, процессора, сетевого трафика и памяти по контейнерам и так далее).

Rollback стратегия. 

Для отката на предыдущую версию реализован отдельный пайплайн, Jenkinsfile которого находится на jenkins/rollback/Jenkinsfile относительно репозитория. Для отката берем последний успешный билд, смотрим в console output строчку  "Building commit XXXXXXXX" (где XXXXXXXX - это хеш коммита и по совместительству тег образов на dockerhub). Далее просто заходим в джоб "anime-backlog-rollback" в дженикс, выбираем "Build with Parameters" и в поле ROLLBACK_SHA вставляем хеш коммита, который хотим восстановить на продакш сервере.
